Actividad práctica realizada

Como aplicación práctica del modelo moderno de desarrollo de software descrito
en el informe, se diseñó un Sistema de Gestión de Tareas orientado a una
empresa de desarrollo de software en Ecuador. El propósito del proyecto fue
demostrar, mediante una solución pequeña y verificable, la integración entre
desarrollo basado en especificaciones, control de versiones, colaboración,
persistencia de datos y automatización de la calidad.

La especificación funcional se organizó en el archivo specs/spec.md. Este
artefacto define el alcance del producto, los actores, las historias de
usuario, los requisitos funcionales y no funcionales, el contrato de datos y
los criterios de aceptación. De esta manera, la especificación se utilizó como
fuente de trazabilidad para orientar la implementación y para relacionar cada
requisito con las verificaciones que deben ejecutarse durante el desarrollo.

El frontend se planteó con Angular y componentes standalone. Para separar la
presentación del acceso a datos se incorporó el servicio TareaService, que
consume mediante HttpClient la API REST del sistema y utiliza la interfaz
TypeScript Tarea para conservar un contrato tipado entre la aplicación cliente
y el backend.

El backend se implementó conceptualmente con Node.js y Express. La API expone
los endpoints GET, POST, PUT y DELETE bajo la ruta /api/tareas, valida el
título y el estado de cada solicitud, y devuelve códigos HTTP diferenciados
para operaciones exitosas, datos inválidos y recursos inexistentes. La
persistencia se definió en PostgreSQL mediante la tabla tareas, cuyos campos
principales son id, titulo, descripcion y estado. Las consultas parametrizadas
evitan interpolar directamente los valores recibidos desde el cliente.

El trabajo se preparó para organizarse mediante Git Flow simplificado. La
estructura y la documentación definen ramas feature/* creadas a partir de main,
commits pequeños y Pull Requests como mecanismo de integración. La creación del
repositorio remoto, las revisiones cruzadas y la protección de main quedan como
actividades operativas pendientes de ejecutar en la cuenta de GitHub del equipo;
por tanto, deben respaldarse posteriormente con sus enlaces y capturas reales.

La automatización se definió en .github/workflows/ci.yml. El pipeline está
preparado para ejecutarse en un runner Ubuntu cuando se realiza un push o un
Pull Request hacia main. Sus etapas instalan las dependencias con npm ci,
ejecutan las pruebas del backend, el linter de Angular, las pruebas unitarias
en ChromeHeadless y la compilación de producción. En la validación local, las
pruebas del backend y las tres pruebas unitarias de Angular finalizaron
correctamente, al igual que el lint y el build de producción.

Finalmente, la solución evidencia que SDD, GitHub, Pull Requests y GitHub
Actions no son prácticas aisladas. La especificación establece qué debe
construirse, las ramas y revisiones controlan cómo se incorpora el trabajo, y
el pipeline proporciona una comprobación automática de la calidad. El
resultado es un flujo reproducible que mejora la documentación, la
colaboración y la confiabilidad del Sistema de Gestión de Tareas.
